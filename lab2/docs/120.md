# MoE S1--S4 新一轮优化计划与实现说明

记录日期：2026-08-03

## 1. 目标与当前判断

本轮目标是在保持参考实现语义和正确性检查通过的前提下，使四个正式场景的加速比分别达到：

| 场景 | 参数 `(N, D, H, E, K)` | 目标 Speedup |
|---|---:|---:|
| S1 | `(1, 256, 128, 16, 4)` | 26.0x |
| S2 | `(1, 1024, 512, 16, 4)` | 19.0x |
| S3 | `(128, 256, 128, 16, 4)` | 150.0x |
| S4 | `(1024, 512, 128, 512, 2)` | 275.0x |

VTune Hotspots 已把 S3/S4 的主要时间归到 `moe_forward_optimized`。结合当前实现继续向下拆分后，可以看到大矩阵本身已经使用 AMX，下一步的收益主要来自减少前向函数内部仍然存在的无效工作，而不是简单增加线程：

1. S4 的 Router 仍对 `1024 x 512 x 512` 做完整 FP32 计算；
2. 路由专家平均只接收约 4 个 token，但当前 AMX Tile 固定配置成 16 行，其余行补零后仍参与计算；
3. batch 路径依次执行 prepare、shared、routed、combine 四次线程池发布；
4. shared expert 的输入本来连续，却仍被复制到线程栈上的临时 `aq`；
5. S3 中同一专家通常有相邻的两个 16-token 块，当前两次执行会重复流式读取相同权重。

本机在仅运行 optimized 路径时测得的改动前参考时间约为 S1 `3.9 us/call`、S2 `33.6 us/call`、S3 `86--103 us/call`、S4 `3.15--3.26 ms/call`。该机器当前未受作业系统的 16-CPU 隔离，绝对时间不能直接代替正式加速比；最终验收仍以同一次正式 driver 输出的 `Baseline time / Optimized time` 为准。

## 2. 准备实施的优化方向

### 2.1 S4：INT8 粗筛加 FP32 精确复核的两级 Router

专家 FFN 已经需要把每个 token 量化成 INT8，因此 S4 可以先量化输入，再复用同一份 `xq` 做 Router 粗筛。预处理阶段额外把 FP32 Router 权重按 expert 做对称 INT8 量化，并打包为 AMX B Tile：

```text
FP32 x
  -> per-token INT8 xq
  -> AMX INT8 Router，得到全部 512 个近似 logit
  -> 按 sigmoid(logit) + bias 选出一小组候选专家
  -> 只对候选专家重算原始 FP32 dot 和 sigmoid
  -> 在精确结果中执行 Top-K
```

粗筛只决定“需要精确复核谁”，最终 gate 和 Top-K 排序仍来自原始 FP32 Router 权重，不能直接用近似分数输出。实现后会扩大候选数并用多组随机 token 检查候选召回；若候选漏召回，就回退到完整 FP32 Router，不能以错误路由换性能。

这一改动把 S4 的主要 FP32 Router 工作从“精确计算 512 个专家”缩减为“AMX 粗算 512 个专家 + 精算少量候选”。S1--S3 的专家数只有 16，继续走现有 FP32 Router，避免粗筛固定成本。

### 2.2 S4：按真实 occupancy 执行稀疏 AMX

当前 `pool.dispatch(..., tile_rows=16, ...)` 使每个 routed expert 都使用 16 行 Tile。S4 共 `N*K=2048` 条路由记录，分到 512 个专家后平均 occupancy 只有 4；固定 16 行意味着多数 routed AMX 指令约四分之三的行在和零计算。

计划在建立 expert bucket 后生成紧凑的 routed chunk 列表：

```text
task = { expert, bucket_start, real_rows }
```

任务按 `real_rows` 分组，工作线程只在行数变化时加载一次对应 Tile config。这样既跳过空专家，又让 AMX 的 M 维等于真实行数。S3 中的完整 16 行块仍保持原配置，避免损失满 Tile 吞吐。

### 2.3 S3/S4：合并 prepare 与 shared，消除连续输入复制

shared expert 不依赖 Top-K，只依赖已经量化的 token。因而每个 token block 可以在完成 Router/Top-K/量化后立即计算 shared expert，把两次线程池发布合成一次。同时：

- 完整 16-token 块直接把 `pw.xq + first * D` 作为 AMX A 矩阵；
- 仅尾块才复制和补零；
- 残差 `x` 的复制与 shared 输出写回合并到向量化 emit 阶段。

正式 S3/S4 的 `N` 都是 16 的倍数，因此热路径不再需要 `run_shared_chunk` 中的栈上 `aq` 搬运。

### 2.4 S3：双 16-token 块复用一次专家权重

S3 每个 routed expert 通常包含约 32 个 token。当前两个 16 行 AMX 调用都会重新加载整套 Gate/Up/Down 权重。计划增加 32-row 专用微内核：用两组 C Tile 保存两个 16-row batch 的累加结果，每次加载一个 B Tile 后同时更新两组结果。

受 8 个 Tile 寄存器数量限制，Gate/Up 按一个输出块、Down 按两个输出块推进。该方案需要实测权重流量下降是否大于并行累加链减少的代价；若微基准没有稳定收益，将不保留该路径。

### 2.5 S1/S2：保护现有快路径并压低固定延迟

S1/S2 不进入新的 batch Router 和稀疏 chunk 路径。针对目标仍会做两项独立检查：

- S1 取消已知收益不稳定的 Router/专家融合等待，比较“先路由、再五个完整 VNNI 专家一次发布”的稳定延迟；
- S2 保留 AMX 输出块着色和 L2 归属，只优化线程池发布、完成检测及最终合并中的固定指令数。

所有 shape specialization 都必须由运行时维度选择，通用 fallback 保留，不能改变接口或依赖输出缓存。

## 3. 实施与验收方法

优化按以下顺序推进，每一步单独测量，负收益改动立即撤销：

1. 建立 S1--S4 optimized-only 短基准和完整正确性基线；
2. 合并 batch prepare/shared 并去掉连续输入复制；
3. 加入真实行数 AMX chunk 调度；
4. 加入 S4 两级 Router，并验证候选召回和最终输出；
5. 评估 S3 双块微内核；
6. 单独收敛 S1/S2 固定延迟；
7. 连续多轮运行四场景，最后执行正式 driver、`git diff --check` 和代码审查。

正确性验收不仅看一次输出：需要覆盖 driver 轮转的输入批次、新 seed 验证批次，以及边界 shape 的 fallback。性能结果取稳定重复值，不采用偶然的单次最好值。本文后续章节会在代码完成后补充实际保留的实现、代码位置、正确性误差和最终 S1--S4 加速比。
