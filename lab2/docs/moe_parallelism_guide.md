# MoE 前向计算中的并行机会

本文根据本实验的 MoE 前向流程，整理可以利用的并行层次、各层之间的数据依赖，以及不同评测场景适合采用的并行策略。本文只解释优化方向，不提供 Lab 的完整实现。

## 1. 并行层次概览

MoE 前向计算中的并行大致可以分成三类：

1. **线程级并行**：把不同 token、不同专家或不同矩阵行交给多个 CPU 线程。
2. **数据级并行**：使用 AVX-512、VNNI 等 SIMD 指令同时处理多个元素。
3. **矩阵级并行**：把多个 token 组成矩阵，使用 AMX Tile 执行 INT8 矩阵乘法。

这些并行方式可以组合。例如，在多个线程之间分配专家，每个线程内部再使用 SIMD 或 AMX。但不宜在所有层次同时创建线程，否则容易产生嵌套并行、线程过量、频繁同步和缓存争用。

## 2. Token 之间并行

不同 token 的前向计算在数学上完全独立：

```cpp
for (int t = 0; t < num_tokens; t++) {
    forward_one_token(...);
}
```

因此可以把不同 token 分配给不同线程：

```cpp
#pragma omp parallel for schedule(static)
for (int t = 0; t < num_tokens; t++) {
    // 每个线程处理不同的 token
}
```

每个 token 都有独立的：

- 路由亲和度数组。
- Top-K 专家编号。
- 路由权重。
- INT8 输入 `xq`。
- 专家隐藏层临时数据。
- 最终输出行 `y[t]`。

只要这些临时数据是线程私有的，不同线程就不会发生写冲突。

这种方式最适合：

- S3：`N = 128`
- S4：`N = 1024`

它不适用于 S1、S2，因为这两个场景都只有一个 token。

### 注意事项

不要将所有线程共享的静态临时数组直接作为每个 token 的工作区，例如：

```cpp
static int8_t xq[MAX_D_MODEL];
```

多个线程同时写入这样的数组会产生数据竞争。临时数组应当是循环体内的局部变量、明确标记为线程私有，或者为每个线程预留独立区域。

## 3. Router 的专家维并行

对于同一个 token，每个路由专家的亲和度可以独立计算：

```cpp
for (int e = 0; e < num_experts; e++) {
    affinity[e] = sigmoid(dot(w_router[e], x));
}
```

因此存在两层并行：

- 不同专家 `e` 的路由分数可以并行计算。
- 每个点积内部的 `d_model` 个 FP32 乘加可以 SIMD 向量化。

S4 中有 512 个路由专家，专家维并行度较高。

### Top-K 是否需要并行

所有路由分数算完后，需要选择 Top-K。理论上可以使用并行归约或并行选择算法，但本实验中：

```text
top_k <= 4
```

K 很小，通常先并行计算所有分数，再串行选择 2 个或 4 个专家更合适。为 Top-K 单独创建线程或执行复杂并行选择的开销可能超过收益。

选择时使用：

```cpp
selection_score[e] = affinity[e] + w.bias[e];
```

路由权重归一化仍然使用未加偏置的 `affinity[e]`。

## 4. 输入量化并行

每个 token 的输入量化分为三个阶段：

```text
求 max(abs(x)) -> 计算 s_x -> 逐元素量化
```

首先计算：

$$
x_{\max}=\max_d|x[d]|
$$

这是一个最大值归约，可以使用 SIMD 在多个向量元素上并行计算局部最大值，最后将向量寄存器中的局部结果归约为一个标量。

得到：

$$
s_x=x_{\max}/127
$$

之后，每个输入元素的量化相互独立：

$$
x_q[d]=\operatorname{round}(x[d]/s_x)
$$

因此量化循环也可以 SIMD 并行。

### 数据依赖

必须先完成整个输入向量的最大值归约，才能计算 `s_x` 并开始量化。不能让一部分线程在最大值尚未确定时提前量化。

## 5. 不同专家之间并行

对一个 token 来说，共享专家和所有被选中的路由专家彼此独立：

```text
共享专家
路由专家 1
路由专家 2
路由专家 3
路由专家 4
```

理论上最多存在：

```text
top_k + 1
```

个独立专家任务。

但本实验中 `top_k <= 4`，如果每处理一个 token 就为这几个专家单独创建线程，线程调度和同步开销可能超过计算收益。这种并行更适合以下情况：

- 已经存在一个持久的 OpenMP 并行区域。
- S2 中单个专家的矩阵规模较大。
- 已经将多个 token 按专家聚集，以专家为较大的并行任务。

### 输出合并的数据竞争

多个专家不能同时直接执行：

```cpp
y[t][d] += gate * expert_output[d];
```

否则多个线程会同时读写 `y[t][d]`，产生数据竞争。

可行的组织方式包括：

- 每个专家写入独立的临时输出，所有专家完成后再统一归约。
- 每个线程维护自己的局部累加结果，最后合并。
- 让同一个线程负责一个 token 的最终输出合并。

## 6. 按专家聚集 token

这是大 batch MoE 中最重要的优化方向之一。

参考实现以 token 为中心：

```text
token 0 -> 专家 3、7、10、12
token 1 -> 专家 3、5、10、15
token 2 -> 专家 3、7、11、12
```

这样专家 3、7、10 等权重会被不同 token 反复读取。可以先根据路由结果，把 token 按专家重新组织：

```text
专家 3  -> token 0、1、2
专家 5  -> token 1
专家 7  -> token 0、2
专家 10 -> token 0、1
专家 11 -> token 2
专家 12 -> token 0、2
专家 15 -> token 1
```

之后，每个专家独立处理属于自己的所有 token：

```cpp
#pragma omp parallel for schedule(dynamic)
for (int e = 0; e < num_experts; e++) {
    process_all_tokens_for_expert(e);
}
```

这种组织方式的优点包括：

- 不同专家可以由不同线程处理。
- 同一个专家的权重可以被多个 token 复用。
- 减少逐 token 反复读取完整专家权重的问题。
- 可以把矩阵向量乘转换成矩阵矩阵乘。
- 更适合使用 AMX Tile。

### 负载均衡问题

不同专家接收到的 token 数可能相差很大。如果直接使用：

```cpp
schedule(static)
```

某些线程可能很快完成冷门专家，而另一些线程长时间处理热门专家。专家级任务可以考虑 `dynamic` 或 `guided` 调度，但动态调度本身也有运行时开销，需要根据实际性能测试选择。

### 分发与回写

按专家聚集通常需要几个阶段：

1. 为所有 token 计算路由和 Top-K。
2. 统计每个专家收到多少 token。
3. 为每个专家计算 token 存储区间。
4. 将 token 或 token 索引分发到对应专家。
5. 并行计算专家输出。
6. 根据原 token 编号和 gate 权重回写、合并输出。

这些阶段之间存在依赖，需要正确设置 barrier 或采用等价的同步方式。

## 7. 专家投影矩阵的输出行并行

每个专家包含三个矩阵：

```text
W_gate : [H][D]
W_up   : [H][D]
W_down : [D][H]
```

### Gate projection

对每个中间维度 `f`：

$$
h_g[f]=W_g[f,:]\cdot x_q
$$

不同 `f` 的输出相互独立，所以 `d_ff` 行可以并行计算。

### Up projection

同理：

$$
h_u[f]=W_u[f,:]\cdot x_q
$$

不同输出行也可以并行。

### Down projection

对每个输出维度 `d`：

$$
o[d]=W_d[d,:]\cdot h_q
$$

不同 `d` 的输出相互独立，所以 `d_model` 行可以并行。

这种线程级并行适合只有一个 token 的 S1、S2，尤其是：

```text
S2: D = 1024, H = 512
```

但是，不应为 gate、up、down 的每个循环分别反复创建 OpenMP 并行区域。更合理的方式是复用一个并行区域，并在必要的位置进行同步。

## 8. 点积内部的 SIMD 并行

所有评测场景都可以使用点积内部的数据级并行。

标量 INT8 点积类似：

```cpp
int32_t acc = 0;
for (int d = 0; d < d_model; d++) {
    acc += (int32_t)weight[d] * (int32_t)activation[d];
}
```

可以使用以下方式并行处理多个元素：

- 编译器自动向量化。
- AVX-512 整数指令。
- AVX-512 VNNI 点积指令。
- AMX INT8 矩阵点积。

这种并行发生在单个 CPU 核心内部，不需要创建线程。

需要保证：

- INT8 输入的有符号语义正确。
- 乘积使用 INT32 累加。
- 最后的水平归约不会丢失任何向量 lane。
- 使用的 intrinsic 与权重、激活的符号类型匹配。

## 9. Gate 和 Up 投影之间并行

Gate projection 和 Up projection 使用同一个输入 `xq`，但读取不同权重，彼此之间没有数据依赖：

```text
Gate projection --+
                  +--> SiLU(gate) * up
Up projection ----+
```

可以采用以下方式利用并行性：

- 同时维护 gate 和 up 的多个累加器。
- 在加载一块输入后，交错处理 gate 和 up 权重。
- 在矩阵分块中同时计算两种投影。
- 对规模足够大的任务，将两种投影分配给不同线程。

通常，单线程内交错计算比为 gate 和 up 单独启动线程更实用，因为它能增加独立指令数量，并有机会复用输入缓存。

## 10. 隐藏层激活与重量化并行

得到 `hg[f]` 和 `hu[f]` 后，每个隐藏元素的激活相互独立：

$$
h[f]=\operatorname{SiLU}(h_g[f])h_u[f]
$$

所以可以使用 SIMD 同时处理多个 `f`。

随后需要计算：

$$
h_{\max}=\max_f|h[f]|
$$

这是最大值归约。得到：

$$
s_h=h_{\max}/127
$$

之后，每个元素的重量化再次相互独立：

$$
h_q[f]=\operatorname{round}(h[f]/s_h)
$$

### 数据依赖

必须遵守下面的顺序：

```text
计算全部 h
    -> 完成 max(abs(h)) 归约
    -> 计算 s_h
    -> 量化全部 h
    -> 执行 down projection
```

如果由多个线程共同完成这些阶段，需要在阶段之间正确同步。

## 11. 共享专家的批量并行

共享专家对所有 token 都执行，因此它天然是一个稠密批处理：

```text
所有 token -> 同一个共享专家
```

与路由专家不同，共享专家不需要先判断哪些 token 被选中。可以直接将整个 batch 组织成矩阵，批量执行共享专家的 gate、up 和 down projection。

这使共享专家特别适合：

- token 级多线程。
- 矩阵分块。
- AMX INT8 矩阵乘法。
- 复用同一组共享专家权重。

## 12. AMX 的矩阵级并行

单个 token、单个专家主要是矩阵向量乘，无法充分利用 AMX 的矩阵乘能力。按专家聚集 token 后，可以把属于同一专家的多个 token 组成矩阵：

$$
X_{\mathrm{expert}}\in\mathbb{Z}^{M\times D}
$$

然后将多个矩阵向量乘转换为矩阵矩阵乘：

$$
X_{\mathrm{expert}}W_g^T
$$

其中 $M$ 是该专家接收到的 token 数量。

这样可以同时利用：

- 多个 token 的批量并行。
- 多个输出通道的并行。
- INT8 四元素点积并行。
- 权重在 Tile、寄存器和缓存中的复用。

这也是 `index.md` 提示“从 expert 的视角考虑”的含义：从单个 token 看是矩阵向量乘，从一个专家处理多个 token 看则是矩阵矩阵乘。

AMX 所需的权重布局通常与原始行优先布局不同，因此可以在 `preprocess` 中提前打包权重，避免在每次前向计算时重复重排。

## 13. 输出合并并行

最终输出为：

$$
y_t=x_t+o_{\mathrm{shared}}+
\sum_{e\in\mathrm{TopK}}g_eo_e
$$

对固定 token，在所有专家输出准备好之后，不同输出维度 `d` 相互独立：

```cpp
for (int d = 0; d < d_model; d++) {
    y[t][d] = x[t][d] + shared[t][d] + routed_sum[t][d];
}
```

因此输出维度可以 SIMD 并行。

如果多个专家并行生成结果，应避免多个线程直接无保护地累加同一输出元素。可以先存储专家局部结果，再由一个线程或一个 SIMD 循环完成最终合并。

## 14. OpenMP 调度选择

### `schedule(static)`

适合各次循环迭代计算量相近的情况，例如：

- 每个 token 都执行完整的逐 token 流程。
- 投影矩阵的每一行长度相同。
- 共享专家对所有 token 的计算量一致。

优点是调度开销低，数据分配连续。

### `schedule(dynamic, chunk)`

适合任务计算量不均的情况，例如：

- 不同专家接收到的 token 数差异明显。
- 某些专家任务远大于其他专家任务。

线程完成一个任务块后再领取新的任务，有助于减少负载不均，但运行时调度开销更高。

### `schedule(guided)`

开始时分配较大的任务块，之后逐步缩小，试图在调度开销和负载均衡之间折中。

调度方式没有固定最优答案，应在相同线程数、绑核方式和输入形状下实际测量。

## 15. 复用并行区域

连续使用多个：

```cpp
#pragma omp parallel for
```

可能反复进入和退出并行区域。MoE 前向中又有路由、分发、专家计算、合并等多个阶段，因此可以考虑创建一个较大的并行区域：

```cpp
#pragma omp parallel
{
    #pragma omp for
    // 阶段 1

    // 默认 barrier

    #pragma omp for
    // 阶段 2
}
```

每个 `omp for` 末尾默认存在 barrier。如果后续阶段依赖前一阶段的全部结果，就必须保留同步。只有确认后续代码不依赖其他线程尚未完成的数据时，才能使用 `nowait`。

## 16. 四个评测场景的并行重点

| 场景 | 形状 | 主要并行机会 |
| --- | --- | --- |
| S1 | `N=1, D=256, H=128, E=16, K=4` | SIMD、投影矩阵输出行、不同激活专家 |
| S2 | `N=1, D=1024, H=512, E=16, K=4` | SIMD、投影行或 Tile、Gate 与 Up 交错 |
| S3 | `N=128, D=256, H=128, E=16, K=4` | token 并行、按专家聚集、共享专家批处理、AMX |
| S4 | `N=1024, D=512, H=128, E=512, K=2` | token 并行、Router 专家维、专家任务并行、动态负载均衡 |

### S1 和 S2

因为只有一个 token，无法使用 token 级并行。主要依靠：

- 点积内部 SIMD。
- 专家投影矩阵输出行并行。
- Gate 和 Up 投影交错执行。
- 在值得的情况下并行执行不同专家。

S2 的矩阵更大，细粒度线程并行比 S1 更可能抵消线程调度成本。

### S3

token 数较多，专家数量较少。可以考虑：

- 直接按 token 分线程。
- 将 token 按 16 个专家聚集。
- 复用专家权重。
- 将共享专家和路由专家计算转换成批量矩阵乘。

### S4

token 和专家都很多，但每个 token 只选两个路由专家。主要问题包括：

- Router 需要为每个 token 计算 512 个专家分数。
- 专家接收到的 token 数可能非常不均匀。
- 专家权重总量很大，缓存无法同时容纳所有权重。
- 专家任务调度和 token 分发开销不可忽略。

因此需要同时关注 Router 向量化、专家级负载均衡和权重访问局部性。

## 17. 推荐的总体组合

实际实现通常选择一个主要的线程并行层次，再在每个线程内部使用 SIMD 或 AMX：

```text
大 batch：token 或 expert 多线程 + SIMD/AMX
单 token：投影行多线程或单线程 SIMD
```

应避免：

- token、expert、投影行三个层次同时创建线程。
- 在很小的循环中频繁进入 OpenMP 并行区域。
- 多个线程共享同一个临时缓冲区。
- 多个专家直接并发累加同一个输出元素。
- 在所需数据尚未完成时错误使用 `nowait`。
- 为追求并行度而忽略缓存复用和线程调度成本。

并行并不必然带来加速。最终应以实验 driver 的计时结果为准，并分别测试四个评测场景。
